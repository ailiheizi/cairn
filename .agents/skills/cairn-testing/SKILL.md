# Cairn 功能验收

依据用户提供的 `testing.md` 及 2026-10-19 的澄清：不要围绕业务规则
写大量局部测试。先堆齐一个完整、可用的功能，再验收整体结果。
本 Skill 约束工作方法，不扩大仓库 `AGENTS.md` 允许的产品范围。

## 执行顺序

1. 用一句话定义用户要完成的事情和最终可观察结果。复用现有需求及
   todo，不为每个按钮、函数或小改动另建验收计划。
2. 连续完成这个功能的前后端实现和集成。不同 agent 并行实现不同部分，
   共用一个功能验收负责人；不要让每个 agent 各跑一遍回归。
3. 先走一条明确指定的 E2E 或集成流程。需要启动程序时先编译；不要先
   堆单元测试，把真正的使用流程留到最后。
4. 整体流程失败时，沿失败环节做局部诊断。只有实际错误、独立正确性
   标准，或整体验收无法覆盖的具体且受本次改动影响的性质，才考虑新增
   局部测试。整体通过且没有明确缺口，就交付并推进下一项功能。

例如：存入 Word → 按正文或语义找到 → 看见命中段落 → 取出原文件。
在同一流程中确认保存结果、检索来源和下载字节；不要将每个中间调用
分别变成测试，也不要用“后端全绿”代替网页里的真实结果。

## 测什么

- 验证功能最终是否满足用户需求和真实副作用。保存后重新读取、重启后
  找回、将取出文件与独立保留的输入比较，优先于检查内部函数被调用。
- “不测试业务规则”指不将易变产品决策拆成大量局部断言；整体流程仍需
  验证目标行为。不要锁死按钮文案、卡片数量、组件结构或内部调用顺序。
- 算法单元测试须有独立正确性标准。第三方库自身的能力不重复测试；
  只验证 Cairn 的接入、使用结果及必要的失败处理。
- 原件完整性、恢复和授权等已受影响的边界，用真实可观察结果验证。
  可以断言明确的拒绝结果和副作用；不要只检查“没有抛异常”或“不是 X”。
- 同一功能和环境尽量共用一次初始化与一条流程。不同输入用参数化表达，
  每个样本保留精确预期；只有独立生命周期或隔离需要才拆开。

## 控制范围与成本

- E2E 不加入默认测试集，只运行明确选定的单个功能流程。
- 只跑受影响范围，不默认执行全量 Go 或全量 E2E。确需扩大范围时，
  说明具体跨模块影响、当前适用的发布门槛或用户要求，不能仅以“保险”解释。
- 测试通过后，只有代码或运行条件变化影响结果、出现新失败或仍有明确
  缺口，才重复相关部分。文档、翻译、布局或验收脚本修改不触发无关后端回归。
- 先复用既有环境和辅助脚本。不要为本轮小改动新建测试框架、矩阵、
  冻结清单或报告流水线。记录实际结果和必要命令即可。
- 检查脚本失败，先区分脚本问题与产品问题；修正选择器、语言或响应字段后，
  只重跑受影响步骤。已确认成功的存入或导出不要重复执行；结果未知时先核实。

## 失败与收尾

- 不以当前错误状态作为预期，不弱化断言、跳过失败来制造通过。先判断
  是需求变更、实现错误还是测试错误，再改对应部分。
- 优先把新错误样本合入已有流程，避免新增重复“回归测试”。只有证实
  旧测试无效才修改或删除；不要因缺少出处就推断旧断言无效。
- 只改文档时只审阅文档和必要格式，不运行应用测试或构建。
- 汇报用户现在能完成什么、尚未完成什么，以及关键验证结果。测试数量、
  构建次数和报告数量都不能作为产品完成度。
